# Информационный бот лаборанта

Консольная программа на C++ для справочной информации о работе лаборанта, учета рабочего времени и обработки инцидентов в кабинете ИКТ.

## Сборка

```powershell
g++ -std=c++14 .\main.cpp -o .\program.exe
.\program.exe
```

## Code Review & Vulnerability Analysis

Анализ относится к текущей версии `main.cpp`, включающей функции исходного бота и модули учета рабочего времени, дисциплинарных взысканий и протокола реагирования. Предлагаемые изменения сохраняют меню, исходные справочные пункты и контрольный вопрос о 20 часах в неделю.

### 1. Ошибка потока ввода может зациклить программу

**Описание проблемы.** В числовых запросах программа проверяет `cin.fail()`, сбрасывает состояние через `cin.clear()` и удаляет не более 1000 символов. При конце входного потока (`EOF`) повторное чтение сразу снова завершается ошибкой. Например, запустить программу с перенаправленным пустым вводом или отправить конец ввода во время запроса меню: цикл будет бесконечно печатать приглашение. При слишком длинной строке остаток после первых 1000 символов также может продолжить ломать чтение.

**Потенциальные последствия.** Бот перестает отвечать, расходует ресурсы и не доходит до выхода или контрольного вопроса. При запуске в автоматизированной среде задание может зависнуть.

**Предлагаемое решение.** Использовать общий помощник чтения, который различает некорректную строку и завершение ввода, и удалять строку целиком:

```cpp
bool readInt(const string& prompt, int& value) {
    while (true) {
        cout << prompt;
        if (cin >> value) {
            cin.ignore(numeric_limits<streamsize>::max(), '\n');
            return true;
        }
        if (cin.eof()) return false;
        cin.clear();
        cin.ignore(numeric_limits<streamsize>::max(), '\n');
        cout << "Введите целое число.\n";
    }
}
```

Добавить `#include <limits>` и на каждом вызове при `false` завершать текущий сценарий корректно. Это не меняет тексты меню и контрольный вопрос.

### 2. Числа принимаются без проверки допустимых границ

**Описание проблемы.** В `workingTime()` проверяется только, что `days` и `rate` положительны, а `hours` больше нуля. Поэтому ввод вроде `days = 100`, `rate = 3` или `hours = 200` проходит проверку, хотя не соответствует смыслу недельного графика. Номер ноутбука ограничен снизу, но не проверяется на соответствие реальному инвентарному диапазону.

**Потенциальные последствия.** Бот выдает правдоподобно выглядящие, но бессмысленные нормы и дефициты. По таким цифрам можно неверно оценить график сотрудника или принять неверное решение об инвентаре.

**Предлагаемое решение.** Задать доменные пределы и проверять их отдельно от успешности чтения: например, `1 <= days <= 7`, `0 < rate <= 1`, `0 < hours <= 24`; для ноутбука установить диапазон, соответствующий инвентарному реестру. Если реестр не задает верхнюю границу, ограничить положительный номер диапазоном типа и отдельно сообщать, что существование номера не подтверждается программой. Не подменять невалидное значение нулем и повторно запрашивать только соответствующее поле.

### 3. Условие подтверждения рабочего времени противоречит расчету

**Описание проблемы.** Недельная норма считается как `40 * rate`, однако цикл завершается только при `hours == 4`. Четыре часа в день соответствуют норме лишь для пятидневной недели и ставки 0,5. Например, при 4 рабочих днях и ставке 0,5 норма равна 20 часам в неделю, но программа требует 4 часа в день (16 часов в неделю) и затем сообщает «Норма подтверждена».

**Потенциальные последствия.** Итоговый вывод может противоречить показанному дефициту. Сотрудник или проверяющий получает неправильное подтверждение графика.

**Предлагаемое решение.** Сравнивать рассчитанные недельные часы с нормой с небольшим допуском для `double`, а не с магическим значением 4:

```cpp
const double weeklyHours = days * hours;
const double tolerance = 1e-9;
if (weeklyHours + tolerance >= normHours) {
    cout << "Недельная норма подтверждена.\n";
    break;
}
```

Если учебное условие требует именно четыре часа в день для конкретного случая, сначала проверить `days == 5` и ставку `0.5`, иначе объяснить, что заданный контрольный режим применим только к этим параметрам. Сохранить исходное правило 20 часов для 0,5 ставки в справочном пункте и контрольном вопросе.

### 4. Главное меню и контрольный вопрос не обрабатывают нечисловой ввод
Описание проблемы. В main() результаты cin >> choice и cin >> answer не проверяются. Если ввести abc, поток перейдёт в состояние ошибки, а choice или answer останется неопределённым либо старым значением. Поведение меню и контрольного вопроса становится непредсказуемым.
Потенциальные последствия. Бот может вывести ошибку, зациклиться или не принять правильный ответ после ошибочного ввода.
Предлагаемое решение. Читать ввод через общие функции для int, проверять состояние потока и очищать остаток строки. При ошибочном вводе повторно запрашивать число; при EOF корректно завершать программу.

### 5. Паузы в протоколе блокируют меню
Описание проблемы. sabotageProtocol() вызывает sleep_for несколько раз подряд. Пока выполняются паузы, главный поток программы занят и меню не принимает команды. Полный сценарий задерживает возврат к меню примерно на 13 секунд.
Потенциальные последствия. Пользователь не может сразу прервать сценарий или вернуться к меню, даже если запустил его ошибочно.
Предлагаемое решение. Для рабочей версии убрать задержки или сделать их необязательным режимом демонстрации. Если задержки нужны для учебного показа, дать пользователю возможность пропустить их.
